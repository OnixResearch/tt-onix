## L2: TTsim `1x1`, simulated

All attempts used the L1 checkpoint, the `smoke-1x1` mesh,
`ttsim-blackhole-sfpu` (slow dispatch, `TT_METAL_DISABLE_SFPLOADMACRO=1`),
`max_seq_len` 256, and 8 KV pages. On every attempt the device opened,
firmware compiled, and weights loaded (35–63 s).

1. Accuracy preset, prefill (`receipts/L2-ttsim-L1-prefill-attempt1.log`):
   `TT_THROW: Statically allocated circular buffers on core range [0-0 - 3-0] grow to 2044800 B which is beyond max L1 size of 1572864 B`
   in `ttnn.rms_norm` from `distributed_norm.py:108` during the first prefill
   (128-token padded). On a single device, prefill normalizes the full
   7168-wide row. On multichip meshes, `is_distributed_norm` selects the
   distributed norm for `dim > 4096` in prefill (`model_config.py:2564-2573`).
   This is an L1 capacity limit of the single-device path. It is not a TTsim
   gap, and it would be the same on one physical P150.
2. Accuracy preset, decode-only ingestion (`receipts/L2-ttsim-L1-decode.json`):
   `TT_THROW: Statically allocated circular buffers on core range [0-0 - 7-9] grow to 1909632 B which is beyond max L1 size of 1572864 B`
   in the decode QKV DRAM-sharded matmul (`attention.py:599`). The weight is
   BF16 WQKV at full width (7168×9216). TP2 halves N to 4608 per device. This
   is again a single-device capacity limit.
3. Performance preset (BFP8 WQKV), decode-only ingestion
   (`receipts/L2-ttsim-L1-decode-performance.log`). Weights loaded in 40.8 s,
   and the first decode step began dispatching programs: the last runtime log
   line is at 16:11:37, 46 s after the load. The step did not complete within
   the 25-minute bound (`timeout --signal=INT 1500`). The process stayed
   blocked inside the simulator, ignored SIGINT, and was terminated at 16:37.
   No receipt was written because the process never returned to Python. This is
   a simulator-throughput limit of the 1×1 path at this width, not a functional
   diagnostic.

Outcome: attempts 1 and 2 are single-device L1 circular-buffer capacity throws
for a 7168-wide model (rms_norm CB 2,044,800 B and decode WQKV DRAM-sharded CB
1,909,632 B, each against 1,572,864 B). They are not TTsim gaps. Attempt 3 was
bounded out. TTsim 1.10.6 has no `x2` runtime, so it cannot exercise the
production TP2 path. Per AGENTS.md the ladder moved to one bounded hardware
attempt (L3a). `tt-smi -r` reset both cards first (`Resetting all PCI devices: [0, 1]`).

## L3b attempt 1: the full model throws an L1 clash at decoder layer 2

`nanbeige43-p150x2 compare --checkpoint …/nanbeige4.3-33b-c1093c501cc6 --reference reference/full-bf16.pt --cache-root /home/brittonr/models/nanbeige43-cache --receipt receipts/L3b-p150x2-full.json`
(accuracy preset, unpadded MLP). The cold weight-cache build and load took
205.7 s and produced a 40 GB cache. The first prompt's prefill completed. The
first decode step then threw:

`TT_THROW: Statically allocated circular buffers in program 154 clash with L1 buffers on core range [0-0 - 7-9]. L1 buffer allocated at 1218304 and static circular buffer region ends at 1220928`

The throw comes from the MLP FF3 decode `ttnn.linear` (`mlp.py:158`).
`receipts/L3b-p150x2-full-run2.json` reproduced it. Per-layer L1 tracing
(`receipts/L3b-l1-per-layer.json`) recorded persistent worker-L1 of 4,352 B per
bank after the load and after the prefill, unchanged. In decode, the largest
free block shrank from 1,430,400 (layer 0) to 1,405,824 (layer 1) and then to
1,397,632 (layer 2), and the throw came in layer 2. The cause is
fragmentation-driven placement against a near-full program, not a leak.
Unpadded, the 11008-wide per-device MLP gets an 8-core DRAM-sharded grid
(gcd(224, 344) = 8), so the FF3 program's static CBs reach 1,220,928 B of the
1,461,376 B bank. The reduced L2 checkpoint never reaches layer 2, which is why
L3a did not show this.

Fix: the upstream knob `PAD_MLP_CORES` (`model_config.py:2821-2833`; the
Qwen2.5 32B/72B entries use it by default) set to 16. It pads the MLP hidden
size from 22016 to 22528 with zero columns in w1/w3 and zero rows in w2,
which is exact. The decode grid becomes 32 cores. Precision, preset, and gates
are unchanged. The runner sets it for every mesh, records `pad_mlp_cores` in the
receipt, and keys the weight cache path by it, because cache file names do not
include tensor shape. The accuracy-preset device budget becomes 22.19 GB.
`L0-device-free-check-padded.json` passed 40 of 40 checks.

L3a rerun with padding (`receipts/L3a-p150x2-L2-padded.json`): **passed**. All
27 rows have top-1 equal to the reference, with PCC 0.99919–0.99948. The padded
grid changes the K partition and accumulation order of the MLP matmuls, and the
two near-tie rows now resolve to the reference token. The unpadded L3a result
stays recorded above as failed. Padding was adopted to fix the L3b layer-2 L1
clash, not to pass L3a.

Batch 8 diagnostics on the corrected runner (`6v7ydvxc…`), done before any
fault attribution:

- The page table is `argsort(randperm(page_blocks, seed 0)).reshape(batch, page_blocks / batch)`,
  a permutation. Every block id is unique and lies in `[0, page_blocks)`, with
  no modulo, clamp, or reuse. Upstream prefill slices row `idx` and pads it
  with -1 to the KV pool size (`generator.py:502-512`, `:827`, with
  `user_id=0` for the fill). Decode passes the `[batch, width]` table
  unchanged (`model.py prepare_decode_inputs_host`). The bench needs 6 blocks
  per row.
- `bench --batch 8 --page-blocks 512` (`O3-bench-trace-b8-pb512.json`) gives

  other operations 3.404 ms (4.4 %).
- **Inference from the two rows above:** 262.6 GB/s for the whole step and
  289.8 GB/s for the matmul bucket, i.e. 51.3 % and 56.6 % of the p150
  512 GB/s pin rate (public p150 table,
  `.pi/references/tenstorrent/docs-site/core/aibs/blackhole/index.md`),
  or 36.2 GB/s per DRAM-bank sender. The decode matmuls are memory-bound by
  more than 10x: the shape-level compute intensity is about 1.6 FLOP/B
  (analysis figure 1.61; a direct 2·M·N·K recomputation gives about 1.65,
  so treat it as ~1.6). Only 8 DRAM-sharded sender cores stream weights; the
  public p150 table lists 120 Tensix cores, while this run's profiler
  `AVAILABLE WORKER CORE COUNT` field reports 110.
- **Source-read:** the supported prefetcher is the only topology lever that
  targets those senders, and it is closed by arithmetic:
  `is_prefetcher_supported` would use `hidden_dim` from a
  `VERIFIED_MODEL_CONFIGS` entry verbatim (it never reads `PAD_MLP_CORES`).
  With `dim=7168`, `n_kv_heads=8`, `num_devices=2`, `MAX_L1_PER_BANK=850000`
  (the dict covers only 4 and 8 devices), and `BYTES_PER_TILE_BFP8=1088`:

  | hidden_dim | ring | tiles/core | bytes/core | pages_ok | l1_ok |
  |---|---|---|---|---|---|
  | 22016 (unpadded) | 16 | 4928 | 5,361,664 | true | false |
  | 22016 | 32 | 2464 | 2,680,832 | true | false |
  | 22016 | 64 | 1536 | 1,671,168 | true | false |
  | 22016 | 80 | 1200 | 1,305,600 | true | false |
  | 22016 | 112 | 896 | 974,848 | true | false |
  | 22528 (padded) | 16/32/64/80/112 | same as above | same as above | true | false |
  | 22016 | 115 | 690 | 750,720 | true | true |
  | 22528 | 118 | 708 | 770,304 | true | true |
  | 22016/22528 | 120 | 720 | 783,360 | true | true |

  The minimum arithmetic ring is 115 unpadded and 118 padded; a prefetcher
  ring is `receivers_per_sender × 8`, so the smallest multiple of 8 that fits
  is 120. The code only offers `legal_receiver_cores = [1, 2, 3, 8, 10]` per
  sender, so reachable rings are 8, 16, 24, 64, and 80, all of which fail
  `l1_ok` (1,305,600 B at the largest). A 115- or 120-receiver mapping is not
  exposed by the supported path and exceeds the 110 worker cores this run
  reported available. The prefetcher would cover only the attention WQKV/WO
  and MLP w1/w3/w2 decode matmuls; it does not cover the LM head, SDPA,
  collectives, or embedding.
- **Source-read:** `PAD_MLP_CORES=16` is already the L1-fragmentation fix and
  adds 2.3 % MLP bytes. Program config, grid, sharding, page size, and sender
  count are internal, not exposed knobs. Fidelity changes are not
  precision-preserving. Batching is already taken (batch 16 gives 160.81 tok/s
  aggregate at 10.05 per user versus the shipped batch-1 9.966 per user; the P1 package measured 11.178).

**Verdict:** within the supported, precision-preserving knob set, no further
decode lever remains. The remaining theoretical headroom is the 8-sender/burst
topology, reachable only through the closed prefetcher or a hand-built
DRAM-sharded matmul program config. Either needs its own declared experiment,
gates, and re-acceptance; neither is an approved change here. This is a
verdict over the supported knob set, not a proof about unimplemented kernels.

### Ceiling after P8/P9 (arithmetic over measured rows)

With device argmax and the all-BFP8 mix, the batch-32 step is 32 / 443.90 =
72.1 ms (promoted receipt) and the step streams 17.263 GB per device (WQKV/WO
and KV now BFP8), i.e. 239 GB/s: 47 % of the p150 512 GB/s pin rate, against
262.6 GB/s for the pre-P8 BF16-attention step. Per-user decode at batch 1 rose
from 9.97 to 13.1-14.3 tok/s.

The remaining gap is the streaming topology, not host work:

- Each decode matmul's DRAM-sharded grid is `find_grid_k_n`, the largest common
  divisor of K and N tiles capped at 64 cores. With hidden 7168 (K = 224 tiles),
  the MLP at padded 22528 (N = 704 tiles) gets 32 cores (gcd 32), and WQKV at
  N = 144 tiles gets 16 cores (gcd 16). K = 224 = 2^5 * 7 cannot yield 64, so no
  supported shape change raises the reader count.
- The prefetcher remains closed: its L1 requirement with BFP8 tiles is the ring
  arithmetic recorded in the earlier ceiling verdict, and the largest reachable
  ring (80 receivers at 1,305,600 B/core) exceeds `MAX_L1_PER_BANK`.
- P6/P8 removed the host serialisation: 82.5 ms of the pre-P8 108.5 ms step was
  device execution, and the argmax is now on device.

So within the supported, precision-preserving knob set there is no decode lever
left. Raising the 47 % requires a hand-built DRAM-sharded program config or a
prefetcher entry, which means patching the installed `models/` tree; the package
installs `models/` unpatched from the runtime-matched source, so that is a
separate change with its own declared experiment rather than a knob. The batched
prefill lever (P5) still trades greedy-id exactness for 2.1x first-token latency
and stays off.

### P10 attribution correction and P11: batch 64 (rejected, 2026-10-27)

P10's blocker is more specific than the first record said. The failing object is
the decode RoPE *transformation matrix*, not the cos/sin cache:
`ModelArgs.use_qk_fused = not is_multimodal and not use_hf_rope`
(`model_config.py:695`) is True for this model, and `RotarySetup.__init__`
doubles the batch for the fused QK path ("we need to double the batch size in
order to replicate the transformation matrix on double the batch size number of
cores", `rope.py:762-764`). At `max_batch_size=64` the matrix is
`[1, 1, 32*128, 32]` and needs 128 height shards against the P300 (8, 8)
64-core grid; at 32 it needs exactly 64.

P11 removed that specific blocker with a supported argument: `create_tt_model`
exposes `use_hf_rope`, which flips `use_qk_fused` off, so a `--hf-rope` flag plus

```
TT_FATAL @ tt_metal/impl/tensor/spec/tensor_spec.cpp:161:
Shard height 64 must match physical height 32 for width sharded
```

from `model.py:956` through `interleaved_to_sharded`:
`tile_padded_batch_rows = 32 * ceil(max_batch_size / 32)`
(`model_config.py:670`) is 64 at batch 64, while the width-sharded decode
buffers are physical 32-row tiles. The packaged decode dataflow assumes exactly
one 32-row tile per step, so 32 is a hard ceiling for this path - independent of
the allowlist and of the rope choice. Extending the batch axis needs a tile-row
loop in the decode dataflow, i.e. an upstream change, not a packing knob.

## P15: batch-8 write/read block resolution mismatch (2026-10-27)

P14 showed rows 5-7 fail only when their block lists differ from row 0's. P15
tested two hybrid tables through an experiment-only `--page-table-override`
flag, with package `/nix/store/gsszwlsv8m3rnk6bi4s4q47zn4bs52lf-nanbeige43-0.1.0`

| Table | Rows that agree | Rows that diverge (first bad token) |
|---|---|---|
| default, 8 unique rows | 0-4 | 5 (1), 6 (1), 7 (1) |
| `upper-from-0`: 0, 5, 6, 7 share row 0 | 0, 5, 6, 7 (all 128 tokens) | 1-4 (3) |
| `lower-from-5`: 0-5 share row 5 | 0-5 | 6 (1), 7 (1) |

Reading: all eight rows have identical tokens and positions, so any row that
writes a block writes the same K/V as any other row would. Rows that share a

## Batch > 32: feasibility inventory (source-read, 2026-10-27, no device)

P10/P11 showed batch 64 fails at two sites in sequence. This is the full
inventory of the packaged decode dataflow's 32-row-tile assumptions, so the
tile-row loop can be scoped rather than discovered one TT_FATAL at a time. All
paths are relative to the runtime-matched v0.77 source; line numbers are from
this checkout.

**Parameterized by batch (no change needed):** `tile_padded_batch_rows`
(`model_config.py:670`), the decode matmul `m=` operands (`:1330`, `:1381`,
`:1688`, `:1981`, `:1960`), the SDPA decode factory (`num_output_cores = B`,
and its reducer/output lists), the paged update-cache read/write loops (they
iterate over `(row, head)` slots: 128 slots over 64 cores at B=32 already needs
2 passes, 256 at B=64 needs 4), the runner's page table, and the device-argmax
readback (`reshape(-1)[:batch]`).

**Hard 32-row literals that a 64-row step must re-express:**

| Site | Assumption | Required change |
|---|---|---|
| `attention.py:651` | `ttnn.reshape(xqkv_fused, (1,1,batch,keys), (1,1,32,keys))` | reshape per tile row: `(1,1,B,keys) -> (2,1,32,keys)` for B=64 |
| `model_config.py:1885`, `:1919` | width-sharded WO/attention output shard `[tile_padded_batch_rows, dim/num_devices]` | shard height must stay 32 (`model.py:956` enforces it), so the shard grid needs `num_devices * (B/32)` cores |
| `rope.py:762-764`, `:804-846` | transformation matrix repeated `doubled_batch_size` times, grid capped at `(8,8)` | already needs 2 tiles per row; at B=64 (HF-rope path, no doubling) it is exactly 64 shards, so this site is fine once `use_hf_rope=True` |
| `distributed_norm.py:30`, `:42` | `(1,1,32,...)` shards (no distributed norm for B=32 on TP2 decode) | same per-tile-row split |
| `model_config.py:1502` | `(1,1,32,dim/.../cores)` MLP output shard (galaxy branch) | not on this path (non-galaxy), listed for completeness |
| `sdpa_decode` core allocation | `num_cores_available >= B` and `num_output_cores = B` | B=64 needs the whole 64-core grid for output cores and leaves nothing for the head-parallel workers; SDPA would need `sub_core_grids` or a 2-pass batch split |

**Core budget consequence.** At B=64, SDPA needs 64 output cores (`=B`) and 64
reducers over a 64-core grid, while the KV update needs 256 `(row, head)` slots.
Neither is a wall — both iterate — but SDPA cannot also spread a head across
cores, so a batch-64 step would run SDPA at one core per row with no head
parallelism. Whether that is faster than two batch-32 steps (which each stream
the weights once, so aggregate is unchanged) is the open question: batch 64 only
pays off if one 64-row weight stream is cheaper than two 32-row ones, and the
two blockers above must be solved first.

Conclusion: batch > 32 is not a knob and not a one-line patch. It is a dataflow
change across five sites plus an SDPA core-budget decision, and its payoff is
bounded by the DRAM bank bandwidth that P17 showed to be the actual limit. That
makes it a low-priority change relative to its risk, and this inventory is the
prerequisite for anyone who wants to attempt it.

## P18: short-prompt prefill is L1-bound, not grid-tunable (rejected, 2026-10-27)

Measured inefficiency: a 128-token prefill costs 0.158 s per row - 17.263 GB at
109 GB/s and 8.55 TFLOP at 54 TFLOPS - while the same package reaches 167 TFLOPS
at 4096 tokens (2752 tok/s). `prefill_rows = 8` is a hardcoded tuning constant
(`model_config.py:783`) and `matmul_config` derives
`per_core_M = ceil(m / (32 * grid.y))`, so at m = 128 (4 M-tiles) each core gets
one M-tile and every weight tile is multicast 8 ways. P18 exposed the constant
through `NANBEIGE43_PREFILL_ROWS` and tried 2.

Two independent blockers surfaced:

1. **Latent grid-order assumption.** Package
   `/nix/store/i3l44wlwk09r14035nram8hxfyfw7lm2-nanbeige43-0.1.0` failed with
   `MatmulMultiCoreReuseMultiCastProgramConfig: Num output blocks along x (8)
   must be smaller than or equal to the number of columns in compute grid (2)`.
   `find_prefill_grid` returns `(rows, cols)`, but all three prefill call sites
   pass it as `matmul_config(grid_size=(x, y))`; the two orders coincide at 8x8,
   which is why the constant has never been changed.
2. **L1 capacity.** Package
   `/nix/store/h1nwn1922pbgd58lk30rg75gy4zb4q2h-nanbeige43-0.1.0` (knob plus a
   `_prefill_grid` helper returning the tuple `matmul_config` expects, a no-op
   at 8x8) then failed inside the prefill attention matmul
   (`attention.py:1162`) with `TT_THROW: Statically allocated circular buffers
   on core range [0-0 - 7-1] grow to 3199872 B which is beyond max L1 size of
   1572864 B`.

The 8x8 prefill grid therefore exists to keep the attention CBs inside L1: any
smaller row count doubles the per-core work and the CB grows past 1.57 MB. The
short-prefill inefficiency is a property of the fused prefill matmul's blocking,
not of a tunable grid, so TTFT is closed at its measured 0.153-0.361 s (batch 1)
and 5.055 s (batch 32).

The knob and the patch were reverted; `pkgs/` has no diff and the rebuilt tree is
the shipped `/nix/store/gw41z3abwqjnk5g03xzw76l7pp3yjpcr-nanbeige43-0.1.0`.
Receipts: `receipts/P18-bench-b1-pr2.json` (order failure) and
`receipts/P18-bench-b1-pr2b.json` (L1 failure). Both runs stopped before any
throughput was measured, so no prefill numbers are claimed.

## P19: DRAM read-bandwidth probe is invalid (inconclusive, 2026-10-27)

The question: the decode step streams 17.263 GB in 72 ms (240 GB/s, 47 % of the
512 GB/s p150 pin rate), and every dataflow knob that could raise it is closed
(P17 core count within 1 %, prefetcher L1-closed, P18 prefill grid L1-bound). Is
240 GB/s the machine's practical read ceiling, or is half the bus left unused?

Two ttnn probe designs, both invalid:

| Probe | Result |
|---|---|
| `ttnn.sum(dim=-1)` on `[1, 1, 262144, 8192]` BF16 (4.29 GB) | did not complete within 226 s - 256 column tiles per row make it a multi-pass tree reduction |
| `ttnn.sum(dim=-2)` on `[1, 1, 2^n, 512]` BF16 (1.07 GB and 2.15 GB) | 73.7 and 74.0 GB/s, i.e. 3.2x *below* the decode step's own 240 GB/s, so the reduction kernel is the limit and the number says nothing about DRAM |

The declared decision rule (`<= 288 GB/s` closes the question, `>= 360 GB/s`
funds a program-config experiment) is therefore not triggered, and the headroom
question stays open. Answering it needs a dedicated reader kernel streaming from
DRAM - a new kernel, which the campaign rules bar without a measured
bottleneck - or an upstream DRAM microbenchmark; the packaged tests carry only
Ethernet and fabric bandwidth tests
(`tests/tt_metal/deployment/eth/*`, `tests/tt_metal/tt_fabric/*`).

The only bandwidth evidence the campaign has stands unchanged: the P0
replacement profiler measured the matmul bucket at 290 GB/s (69.45 ms for
20.125 GB) and the whole step at 240-247 GB/s, and P17 showed the rate is
insensitive to reader count. No code change was made; the receipt
`receipts/P19-dram-read-bandwidth.json` records the invalid probe so the next
attempt does not repeat it.

## P22: compare's read path is not its overhead (rejected, 2026-10-27)

The committed compare receipts show the accuracy-gate tool decoding slower than
bench with the same trace: 143.1 ms/step at batch 1, 197.7 at batch 2, 1.65 s at
batch 32, against 70-72 ms in bench. P22 tested the obvious suspect -
`decode_rows` reading through `decode_forward(read_from_device=True)` and
`process_decode_output_host` instead of the `read_from_device=False` +
`read_decode_output` + sliced `to_torch` path that bench uses - on package
`/nix/store/l7q0qkif3lb2j2nxnpavfgcnmg2119ry-nanbeige43-0.1.0`.

Numerics were bit-identical to `P9-compare-b1-bfp8`:

- teacher-forced top-1 0.908203125 and top-5 0.994140625,
- corpus prefill PCC 0.9968535197566657 (exact equality),
- the three fixed-prompt PCCs and every `prompts[].rows` report,
- all 511 `predicted` tokens.

That is an independent confirmation of P1/P8 from the opposite direction: the
read path does not alter a single value.

Timing went the wrong way, so the declaration fails: teacher-forced decode 83.6 s

## P23/P24: compare's overhead is torch's thread pool, but the fix misses its bar

P22 eliminated the read path. Host measurement of the runner's own metric
function, on the packaged torch, then isolated the real cost of
`batch_row_report` for one batch-1 step:

| torch threads | `batch_row_report`, batch 1 |
|---|---|
| 32 (default) | 587.96 ms |
| 8 | 40.17 ms |
| 1 | 7.22 ms |

Individual operations at 32 threads on the 83,456-element row: `sort` 61.5 ms, a
mean-subtracted float64 dot 226.4 ms, `abs().max()` 67.4 ms, `std` 44.8 ms. The
thread pool dominates the arithmetic by up to 81x.

P23 (wrapper on `row_report` only) failed its own bit-for-bit gate for a reason
worth recording: torch reduces in float64 with a thread-count-dependent order, so
the corpus PCC moved 0.9968535197566657 -> 0.9968535197566615 and the row reports
cannot stay bit-identical. The fixed-prompt phase did get 2.1-2.6x faster.
Teacher-forced did not improve because it calls `pcc` directly, outside
`row_report` (84.8 s, 166.4 ms/step against 73.1 s, 143.3 ms/step).

P24 repeated the change with the teacher-forced `pcc` covered and declared gates
that admit float64 reduction-order noise (1e-12) plus a 1.5x timing bar:

| Measure | P9 (admitted) | P24 |
|---|---|---|
| teacher-forced decode | 73.1 s (143.3 ms/step) | 53.0 s (103.9 ms/step), 1.38x |
| plain-capital prompt | 28.2 s | 18.2 s, 1.55x |
| chat-sky prompt | 6.6 s | 3.3 s, 2.0x |
| plain-fibonacci prompt | 8.3 s | 3.2 s, 2.6x |
| top-1 / top-5 | 0.908203125 / 0.994140625 | identical |
| 511 predicted tokens | - | identical |
| PCC deltas | - | 4.2e-15 corpus, <= 2.6e-15 prompts |

Numerics passed; the teacher-forced phase improved 1.38x against the declared
1.5x bar, so P23 and P24 were both reverted and the bar was not moved. Gate 3
(`bench`) was not run because gate 2 had already failed.

What the campaign now knows about the harness: the fixed-prompt phase is
metric-bound and responds 1.5-2.6x to single-threading; the teacher-forced phase
is dominated by the device step plus the full-vocabulary readback and `.float()`,
which caps the mixed gain at 1.38x. Reverting restored
`/nix/store/mys4lycvklaw7r18g7lf2b95iaxj2xi6-nanbeige43-0.1.0` byte-for-byte.
Receipts: `receipts/P23-compare-b1.json`, `receipts/P24-compare-b1.json`.
