## 2. Do the matmul reader cores already own DRAM banks one-to-one, or is the access round-robin/interleaved across banks? Cite the bank constants and the sharding helper that decide this.

**The default path uses interleaved DRAM weights, not a configured one-reader-per-bank assignment.** Gate/up/down all pass `ttnn.DRAM_MEMORY_CONFIG` (`mlp.py:109-135`); the 1D builder explicitly requires interleaved weights (`tp_common.py:102-109`). Thus the source-level placement is interleaved across banks, rather than bank-owned worker shards. The exact round-robin page-to-bank order and reader issue schedule are not implemented in these Python files and cannot be asserted from them.

The available bank-related constants are `DRAM_CORES = 8` and `DRAM_GRID = ttnn.CoreRangeSet({ttnn.CoreRange(ttnn.CoreCoord(0, 0), ttnn.CoreCoord(DRAM_CORES - 1, 0))})` (`tp_common.py:15-18`). They define an eight-coordinate `(8,1)` logical DRAM shard grid, **not** a mapping from the 44/33 default worker cores to eight banks. The alternative helper `create_dram_sharded_mem_config(k, n)` pads `n` to a multiple of `TILE_SIZE * DRAM_CORES`, constructs `ShardSpec(DRAM_GRID, (k, padded_n // DRAM_CORES), ROW_MAJOR)`, and returns `MemoryConfig(WIDTH_SHARDED, DRAM, shard_spec)` (`tp_common.py:60-73`). That helper establishes eight width shards for the alternative layout; it does not prove physical reader-core/bank ownership, and default MLP loading bypasses it (`mlp.py:58-62,109-135`).

## 4. Deeper evidence on transactions and rereads (2026-10-22)

**cannot-tell-at-any-device-free-level**

This outcome concerns actual baseline-versus-candidate transactions per decode step under the specified authorities, not an assertion that software-issued request counts are inherently unknowable from a complete compiled program. The specific missing quantity is the actual DRAM-sourced weight request stream for each projection: the multiset of `(source bank, source address, byte length)` requests emitted per step, including duplicate tile reads, padded/edge reads, and transfer coalescing. Neither a selected Qwen TTNN reader/program-factory binding with its instantiated arguments nor a candidate implementation is established by the permitted allocator/examples/guidance. Physical DRAM-controller burst counts and effective bandwidth additionally require runtime observations; they must not be substituted for software NoC request counts.

### Allocator mapping: round-robin is now established

All paths in this section are relative to `.pi/references/tenstorrent/`. In `tt-metal-docs/tt_metal/hw/inc/internal/dataflow/dataflow_api_addrgen.h:18-40`, `get_bank_offset_index<true>(id)` computes `floor(id / NUM_DRAM_BANKS)` (division or a power-of-two shift), and `get_bank_index<true>` returns `id - bank_offset_index * NUM_DRAM_BANKS`. Therefore page `p` maps to bank `p % B` with within-bank page index `floor(p/B)`, not to a bank selected by reader-core identity. Bank coordinates are looked up through `dram_bank_to_noc_xy[noc][bank_index]` (`:44-48`); `InterleavedAddrGen` combines the within-bank aligned-page offset, tensor base, and bank offset (`:285-310`). The same arithmetic is present in `tt-metal-latest/tt_metal/hw/inc/internal/dataflow/dataflow_api_addrgen.h:18-48`. Blackhole has eight DRAM banks, one per channel (`tt-metal-docs/tech_reports/memory/allocator.md:17-23`). This resolves section 2's earlier page-mapping limitation without changing its default-placement conclusion.

### Reader loops: full K does not mean full weight rereads

The explicit example reader `tt-metal-docs/tt_metal/programming_examples/matmul/matmul_common/kernels/dataflow/reader_bmm_tile_layout.cpp:56-94` issues one `noc_async_read_page` for each visited in0 tile (`:66-76`) and each visited in1 tile (`:78-88`), then a barrier (`:90`). The associated documented arguments are `in1_block_w=per_core_N`, `in1_block_h=in0_block_w`, `in1_tensor_next_block_stride=in0_block_w * Nt`, and `num_blocks=Kt / in0_block_w` (`tt-metal-docs/tech_reports/prog_examples/matmul_multi_core_optimized/data_reuse.md:123-133`). Hence for one batch and one assigned output rectangle, the example requests `(Kt/b) * b * per_core_N = Kt * per_core_N` weight pages, where `b=in0_block_w`. It advances along K; it does not restart the same weight slice once per K block. In0 similarly contributes `Kt * per_core_M` page reads for this non-multicast example (`:113-121`). These are example-kernel counts, not claimed observations of the Qwen-selected 1D multicast kernel.

Thus “every core streams the full K” means every output-column partition participates in all K reductions; it does not mean every core reads all N columns of in1. Varying `in0_block_w` changes chunking, circular-buffer requirements, and barrier cadence, not the algebraic `Kt * per_core_N` page count in this example. Activation delivery/multicast must be counted separately from weight DRAM reads: the sharded matmul guidance explicitly multicasts in0 shards to compute workers while each reader reads its own in1 bank partition (`tt-metal-docs/tech_reports/Saturating_DRAM_bandwidth/Saturating_DRAM_bandwidth.md:49-56`).

### Quantified source model, and what remains unknown

For one device, one layer, one decode step and a single tiled weight matrix `[K,N]`, let `Kt=ceil(K/32)` and `Nt=ceil(N/32)`. Under **one read per valid weight tile, disjoint output-column ownership, no extra edge reads, and one page per tile**, both layouts require `Kt * Nt` weight-page reads. A bank-matched eight-way partition changes each reader's share to `Kt * Nt/8` when `Nt` is divisible by eight; the aggregate delta is **0 weight-page reads and 0 weight bytes**. Each tile has one destination bank before and after; changing which bank/core owns it does not eliminate it. This is conditional arithmetic, not a demonstrated baseline request count.

For the whole gate/up/down MLP, the same model gives `2 * ceil(D/32) * ceil((H/2)/32) + ceil((H/2)/32) * ceil(D/32)` weight-page reads per device per layer per step. For full 32×32 BFP tiles the address arithmetic encodes 576 bytes for BFP4 and 1088 bytes for BFP8 (`tt-metal-docs/tt_metal/hw/inc/internal/dataflow/dataflow_api_addrgen.h:81-123`); the corresponding conditional payload is `2*576*ceil(D/32)*ceil((H/2)/32) + 1088*ceil((H/2)/32)*ceil(D/32)` bytes. No 44× or 33× multiplier on the entire weight matrix follows from full-K participation.

Define a transaction explicitly as one emitted NoC read request, not a read API call, response flit, or DRAM-controller command. `noc_async_read_page` determines page size from its accessor and passes it to `noc_async_read` (`tt-metal-docs/tt_metal/hw/inc/api/dataflow/dataflow_api.h:1052-1075`). Blackhole's generic any-length read issues chunks of at most `NOC_MAX_BURST_SIZE`, followed by the remainder (`tt-metal-docs/tt_metal/hw/inc/internal/tt-1xx/blackhole/noc_nonblocking_api.h:859-875`); its maximum is `256 * (512/8) = 16384` bytes (`tt-metal-docs/tt_metal/hw/inc/internal/tt-1xx/blackhole/noc/noc_parameters.h:286-290`). Consequently a positive-length read of L bytes through that path emits `ceil(L/16384)` requests. In the one-page-per-read model, each 576/1088-byte weight tile is one request, so the conditional delta is also **0 NoC weight-read transactions per step**. A candidate that coalesces contiguous bank-local tiles could change request counts without changing bytes: its count would instead be the sum of `ceil(L_i/16384)` over its actual read calls. A 1×8 grid alone does not specify those `L_i`, duplicate multiplicities, or edge handling, so an unconditional numeric baseline-versus-candidate transaction delta is not supported.

### Bank-matching is a congestion hypothesis, not evidence of fewer bytes

The bandwidth report says interleaved readers access banks “in a round-robin style” and motivates sharding to mitigate NoC congestion (`tt-metal-docs/tech_reports/Saturating_DRAM_bandwidth/Saturating_DRAM_bandwidth.md:49-54`). It recommends one assigned reader per bank (`:24`), appropriate physical reader placement and virtual channels (`:26-31`), and overlapping tagged reads rather than stalling at every block barrier (`:9-13`). These mechanisms can improve service time for unchanged payload; none proves fewer weight rereads. The report's measured utilization is for Wormhole/Grayskull (`:1-2`), not a measured Blackhole result. Low-level guidance separately distinguishes one-packet versus chunked transfers at Blackhole's 16 KB scale (`tt-low-level-documentation/data_movement_doc/general/dm_best_practices.md:209-212`). Neither choosing eight logical coordinates nor deriving `per_core_N` establishes favorable physical routing or coalescing.
