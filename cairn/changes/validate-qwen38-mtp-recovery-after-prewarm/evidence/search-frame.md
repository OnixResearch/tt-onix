# Search frame

## Goal

Produce one complete matched persistent-recovery control after exact target prewarm, or preserve the exact bounded blocker.

## Completion evidence

- One loaded process prewarms every fixed prompt.
- Persistent warmups cover both recovery routes for every prompt.
- All sixty measured roots follow the accepted balanced schedule.
- Every target-validation signature matches its prompt prewarm signature.
- The program-cache count stays fixed throughout measurement.
- The existing evaluator receives complete exact state and timing evidence.
- Eager production health is restored after any authorized physical case.

## False completion

- A shorter prompt or route subset replaces the accepted schedule.
- Prewarm and measured signatures differ.
- A measured root compiles a new program.
- A timeout has no atomic root boundary.
- A receipt weakens stability, state, capture, or recovery-ratio gates.
- Diagnostic completion becomes an MTP, traced-decode, or speedup claim.

## Audit risks

- Prompt values can select different acceptance widths and rollback work.
- Persistent and nonpersistent pilots can diverge despite fixed tensor shapes.
- Warmup can hide compilation unless measurement freezes the cache count.
- Progress writes can perturb host scheduling, but they must not enter synchronized recovery timing.
- A complete process can still produce invalid or unstable evidence.

## Approach registry

### Per-prompt prewarm before the accepted full control

- **Family:** Exact same-process compilation control.
- **Mechanism:** Prewarm each prompt once, run both persistent warmup routes, then run the unchanged sixty-root schedule.
- **Claim:** Complete roots can evaluate persistent recovery without cold target-validation compilation.
- **Artifact:** A distinct recovery-control mode, ordered ledger, and unchanged rollback decision.
- **Evidence:** The prompt-2 snapshot path completed after exact prewarm with no measured target-validation cache growth.
- **Gap strength:** Equivalent to the accepted recovery evidence goal.
- **Blocker:** The validated package needs explicit authorization for its `1800`-second command bound and `120`-second termination grace.
- **Next check:** Run the one prepared physical control only after authorization.
- **State:** Active.

### Prewarm one prompt only

- **Family:** Shape-only compilation control.
- **Mechanism:** Use one calibration prompt to warm programs for all prompts.
- **Claim:** Fixed tensor shapes imply one prompt covers the full schedule.
- **Artifact:** A smaller wrapper change.
- **Evidence:** Prompt 2 warmed its own measured route.
- **Gap strength:** Simpler.
- **Blocker:** Token values change acceptance width and rollback work. One prompt does not prove all prompt signatures.
- **Next check:** None while per-prompt prewarm is affordable.
- **State:** Falsified as insufficient evidence.

### Run a short repeated staged subset

- **Family:** Reduced physical control.
- **Mechanism:** Repeat one prompt and both routes without the full profile.
- **Claim:** A short control can estimate recovery stability.
- **Artifact:** A one-prompt repeated ledger.
- **Evidence:** The accepted evaluator requires five prompts and six samples per route and prompt.
- **Gap strength:** Simpler.
- **Blocker:** The subset cannot satisfy acceptance coverage or the existing stability contract.
- **Next check:** None.
- **State:** Falsified.

### Precompile target kernels directly

- **Family:** Synthetic kernel warmup.
- **Mechanism:** Invoke selected target operations before the full model path.
- **Claim:** Direct operation calls remove cold compilation at lower startup cost.
- **Artifact:** Operation-specific warmup code.
- **Evidence:** Prior ledgers localized compilation to target validation but did not identify every program key.
- **Gap strength:** Unknown.
- **Blocker:** Synthetic calls can miss program configurations and do not prove exact output or rollback signatures.
- **Next check:** Use only if full exact prewarm becomes infeasible.
- **State:** Blocked.

### Release the persistent trace before validation

- **Family:** Trace-coexistence control.
- **Mechanism:** Release recovery trace resources before target validation.
- **Claim:** Trace coexistence caused the prior stall.
- **Artifact:** Trace lifetime change.
- **Evidence:** Warm target validation completed while the persistent trace remained valid.
- **Gap strength:** Changes the target persistence contract.
- **Blocker:** It is not required by the checked prompt-2 result.
- **Next check:** None.
- **State:** Falsified as a necessary mechanism.

## Budgets

- Source authority: package-matched Qwen and TT-Metal sources only.
- Retrieval: local accepted specifications, archived evidence, and current source.
- Exploration: correlated serial lenses only; subagent consent is absent.
- Implementation: one exact full-control mechanism.
- Physical: zero cases until the prepared `1800`-second bound and `120`-second termination grace receive explicit authorization.
- Final outcomes: validated, blocked, exhausted, or user-decision-required.
